# 최신경제 문의 접수/처리 로그

실제 문의(댓글, 이메일, 문의 폼 등)가 들어오기 시작하면 이 문서에 기록해 처리 현황을 관리합니다.
FAQ(`cs/faq.md`)와 응답 템플릿(`cs/response-templates.md`)이 "무엇을 어떻게 답할지"에 대한
자료라면, 이 문서는 "실제로 어떤 문의가 들어왔고 어떻게 처리했는지"를 남기는 기록입니다.

마지막 업데이트: 2026-09-21

---

## 1. 사용법

### 1-1. 언제 기록하나

- 사이트 댓글, 이메일, 문의 폼 등 어떤 채널로든 실제 문의가 들어오면, CS팀이 응대를 시작하기
  전 또는 응대 초안을 작성하는 시점에 아래 표에 한 줄을 추가한다.
- 문의가 여러 차례 오가더라도(추가 질문, 재문의 등) 하나의 사안은 원칙적으로 한 행으로 관리하고,
  처리 상태와 비고를 갱신하는 방식으로 업데이트한다. 완전히 다른 사안이면 새 행으로 분리한다.

### 1-2. 표를 채우는 방법

| 컬럼 | 작성 방법 |
|---|---|
| 날짜 | 문의를 접수한 날짜 (YYYY-MM-DD) |
| 채널 | 댓글 / 이메일 / 문의폼 / 기타(구체 명시) |
| 카테고리 | `response-templates.md`의 카테고리 중 선택: ① 사실관계·최신성 / ② 투자·대출 조언 요청 / ③ 오류 신고 / ④ 광고·제휴 문의 / ⑤ 개인정보·환불 등 민감 문의 / ⑥ 콘텐츠 주제 요청 / ⑦ 발행 주기 문의 / ⑧ 응원/감사 피드백. 해당 없으면 "기타"로 표기하고 내용에 설명 |
| 문의 요약 | 문의자의 개인정보(이름, 이메일, 연락처, 주문번호 등)를 그대로 옮기지 않고, 무엇을 물었는지 핵심만 요약. 민감 정보는 "본인 확인 정보 있음" 등으로 마스킹 |
| 사용한 응답/템플릿 요약 | `response-templates.md`의 몇 번 템플릿을 기반으로 어떤 답변을 했는지(또는 할 예정인지) 한두 줄 요약. 초안일 뿐 실제 발송 전이면 "(초안, 미발송)"이라고 표기 |
| 처리 상태 | 처리중 / 답변완료 / 에스컬레이션 대기 중 하나 |
| 에스컬레이션 여부 | 사장/마스터 에스컬레이션이 필요 없으면 "-", 필요하면 "○ (사유)" 형태로 표기 |

### 1-3. 민감 문의 발견 시 에스컬레이션 표시 방법

CLAUDE.md 및 CS팀 작업 원칙에 따라, 아래에 해당하는 문의는 CS팀이 답변을 임의로 확정하지 않고
반드시 사장/마스터에게 에스컬레이션한다. (`response-templates.md`의 2번·4번·5번 카테고리와 동일 기준)

- 투자·대출 등 구체적인 금전적 판단에 영향을 주는 조언 요청
- 개인정보 처리, 환불, 결제 관련 등 민감 문의
- 광고·제휴·협업 제안(조건/비용 확정이 필요한 사안)
- 그 외에도 CS팀 판단으로 사장/마스터 확인이 필요하다고 보는 사안

참고로 ⑧ 응원/감사 피드백처럼 특별한 조치가 필요 없는 단순 긍정 피드백은 에스컬레이션 대상이
아니다. 다만 그 안에 실제 요청/질문이 섞여 있으면 해당 카테고리 기준으로 별도 판단한다.

이런 문의를 발견하면 표에 다음과 같이 남긴다.

1. **카테고리**: 해당하는 번호(②/④/⑤)를 명시한다.
2. **처리 상태**: "에스컬레이션 대기"로 기록한다. (사장/마스터 확인 전까지 "답변완료"로 표기하지 않는다.)
3. **에스컬레이션 여부**: "○ (사유)" 형태로 구체적으로 남긴다. 예: "○ (환불 요청, 사장 확인 필요)".
4. **사용한 응답/템플릿 요약**: 실제 확정 답변이 아니라 "1차 안내만 발송(확인 후 안내 예정)" 등으로,
   무엇을 임의로 확정하지 않았는지가 드러나도록 적는다.
5. 사장/마스터의 확인·지시가 내려오면 처리 상태를 "답변완료"로 갱신하고, 최종적으로 어떻게
   처리됐는지 요약을 덧붙인다.

### 1-4. 그 외 유의사항

- 이 로그 자체가 개인정보 저장소가 되지 않도록, 이메일 주소·전화번호·결제 정보 등은 표에
  직접 기재하지 않는다. 필요하면 "연락처 확보됨"처럼만 표기한다.
- 오류/불만 신고 건은 이 로그에도 남기되, 개발팀/기획팀 전달용 상세 정리가 필요하면
  별도로 요약해 전달한다(response-templates.md 3번 카테고리 참고).
- 표가 길어지면 월 단위로 섹션을 나누거나 별도 파일로 아카이브하는 것을 고려한다(현재는 문의가
  없어 단일 표로 시작).

## 2. 문의 접수/처리 표

> 아래 2건은 실제 문의가 아니라, 표 사용법을 보여주기 위한 **가상의 예시**입니다.
> 실제 문의가 들어오기 전까지 이 표에는 예시 외의 실제 데이터가 없습니다.

| 날짜 | 채널 | 카테고리 | 문의 요약 | 사용한 응답/템플릿 요약 | 처리 상태 | 에스컬레이션 여부 |
|---|---|---|---|---|---|---|
| 2026-09-15 (예시) | 댓글 | ① 사실관계·최신성 | "글에 나온 기준금리 수치가 최근 발표와 다른 것 같다"는 댓글 | 템플릿 1번 기반으로 "작성일 기준 정보이며 최신 수치는 한국은행 발표 확인 권장, 확인 후 필요시 보완" 안내 (초안, 미발송) | 처리중 | - |
| 2026-09-15 (예시) | 이메일 | ⑤ 개인정보·환불 등 민감 문의 | "결제 관련 문제가 있어 환불을 요청한다"는 이메일 (연락처 확보됨) | 템플릿 5번 기반으로 "CS팀이 임의로 확정 어려워 담당자에게 전달, 확인 후 안내" 1차 안내만 발송 예정 (초안, 미발송) | 에스컬레이션 대기 | ○ (환불 요청, 사장/마스터 확인 필요) |

## 3. 개발팀·기획팀 전달용 오류·불만 신고 요약 양식

이 로그의 표(2번)에는 오류/불만 신고 건도 한 줄 요약으로 남기지만, 개발팀 또는 기획팀에 실제로
수정을 요청하려면 표 한 줄만으로는 정보가 부족하다. 사이트 오류·콘텐츠 오류 신고가 접수되면,
아래 항목을 채워 이 섹션(또는 신고 건별로 아래 형식을 복사해 추가한 하위 항목)에 정리한 뒤
개발팀/기획팀에 전달한다. `response-templates.md` 3번 카테고리(오류/오탈자 신고)와 짝을 이루는
전달용 양식이다.

### 3-1. 언제, 어떻게 쓰나

- 방문자가 오탈자, 사실관계·수치 오류, 사이트 기능 오류(로딩 안 됨, 버튼 작동 안 함 등), 깨진 링크
  등을 신고하면, CS팀은 먼저 2번 표에 한 줄을 남기고, 개발팀/기획팀에 실제로 전달이 필요하다고
  판단되면 아래 항목표를 이용해 신고 건을 정리한다.
- 신고가 여러 건 쌓이면 이 섹션 아래에 신고 건별로 표를 반복해서 추가한다(날짜순).
- 정리한 내용은 CS팀이 임의로 "이렇게 고쳐야 한다"고 결론 내리지 않고, 신고 내용과 사실관계를
  있는 그대로 전달하는 데 집중한다. 원인 분석과 수정 여부/방법 판단은 전달받는 개발팀/기획팀의
  몫이다.

### 3-2. 전달용 항목

| 항목 | 작성 방법 |
|---|---|
| 접수일 / 채널 | 신고가 들어온 날짜(YYYY-MM-DD)와 채널(댓글/이메일/문의폼/기타) |
| 대상 글 또는 페이지 | 문제가 발생한 글 제목과 링크(또는 경로). 특정 글이 아니라 사이트 전반의 기능 문제라면 "사이트 전반" 또는 해당 페이지 범위를 명시 |
| 문제 유형 | 다음 중 선택하거나 해당 없으면 "기타"로 명시하고 설명 추가: (a) 오탈자 (b) 수치·사실관계 오류 (c) 사이트 기능 오류 (d) 링크 깨짐 (e) 기타 |
| 구체적 문제 내용 | 신고자가 말한 내용을 최대한 그대로, 어느 문단/문장/수치/버튼인지 구체적으로 기술. CS팀이 임의로 "오류가 맞다/아니다"를 단정하지 않고 신고된 내용 그대로 전달 |
| 재현 방법 (사이트 기능 오류인 경우) | 어떤 기기/브라우저에서, 어떤 순서로 조작했을 때 문제가 발생했는지. 신고자가 밝히지 않았다면 "확인 안 됨"으로 표기하고, 필요시 신고자에게 되물어 보완 |
| 전달 대상 | 개발팀, 기획팀, 디자인팀 중 어디로 보내는지와 그 이유를 함께 기재. 기준: 사이트 기능·기술 오류(로딩 안 됨, 버튼/링크 작동 안 함, 깨진 링크 등) → 개발팀 / 콘텐츠 내용(오탈자, 수치·사실관계 오류, 다루는 주제 관련) → 기획팀 / 화면 표시·가독성·색상·레이아웃(글자 크기, 줄 간격, 색상 대비, 표·카드뉴스 디자인 등) → 디자인팀. 둘 이상에 걸치면 해당하는 곳 모두에 전달하고 그 이유를 적는다 |
| 심각도/긴급도 | 다음 기준으로 CS팀이 1차 판단하되, 최종 우선순위는 전달받는 팀/마스터 판단에 따름. 높음: 사이트 접속·핵심 기능 자체가 안 됨, 또는 명백한 금전적·사실관계 오류로 신뢰에 영향 / 중간: 특정 글·페이지의 기능 오류, 또는 눈에 띄는 수치 오류 / 낮음: 단순 오탈자, 사소한 표현 오류 |
| 신고자 재확인 필요 여부 | 신고 내용이 불충분해 개발팀/기획팀 전달 전 추가 확인이 필요하면 "필요 (사유)", 아니면 "불필요" |

### 3-3. 작성 예시 (가상 예시, 실제 데이터 아님)

> 아래는 형식을 보여주기 위한 예시이며 실제 신고 건이 접수되기 전까지는 예시 외 실제 데이터가
> 없다.

| 항목 | 내용 |
|---|---|
| 접수일 / 채널 | 2026-09-19 (예시) / 댓글 |
| 대상 글 또는 페이지 | "2026년 기준금리 전망" (링크 미정, 예시) |
| 문제 유형 | (b) 수치·사실관계 오류 |
| 구체적 문제 내용 | 신고자가 "본문 중 기준금리가 3.5%로 적혀 있는데 실제 발표는 3.25%인 것 같다"고 댓글 남김 |
| 재현 방법 | 해당 없음(콘텐츠 오류이므로) |
| 전달 대상 | 기획팀 (콘텐츠 수치·사실관계 오류이므로) |
| 심각도/긴급도 | 중간 (수치 오류이나 사이트 기능에는 영향 없음) |
| 신고자 재확인 필요 여부 | 불필요 (신고 내용 자체로 확인 가능한 수준) |

지속적으로 업데이트합니다. 예시 항목은 실제 데이터가 아니므로 통계나 보고에 포함하지 않습니다.*
