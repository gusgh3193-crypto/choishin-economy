**완료한 일 (마스터 재검증 완료)**

  padding(좌우 각 16px)을 측정해 두 항목 모두 PASS로 보고. `overflow-x: auto` 항목은 computed
  `overflowX: auto`로 CSS는 정상 적용돼 있으나, 이 글의 실제 표 콘텐츠로는 375px/320px 모두
  `scrollWidth`와 `clientWidth`가 같아(343=343, 288=288) 실제 가로 스크롤이 발생하지 않음을
  발견했다. 메커니즘 자체가 고장난 것인지 구분하기 위해 `table-overflow-mechanism-test.js`로
  브라우저 런타임에서만(디스크 미변경) `th, td { white-space: nowrap !important; }`를 임시
  주입해 넘침 상황을 시뮬레이션한 결과, 320px에서 `scrollWidth: 298 > clientWidth: 288`로 실제
  오버플로가 발생했고 `scrollLeft` 이동도 실제로 동작함(scrolled: true)을 확인해 **메커니즘
  자체는 정상(PASS), 다만 이 글의 콘텐츠로는 가로 스크롤 상황 자체가 생기지 않는다**는 결론을
  보고.

  스크립트를 Read로 직접 읽어 로직을 확인한 뒤 동일 환경에서 직접 재실행(`node mobile-check.js`,
  `node table-overflow-mechanism-test.js`)해 완전히 동일한 수치(16px, 16px/16px,
  343=343/288=288, nowrap 시뮬레이션 298>288/scrolled:true)를 얻었다. `mobile-375x667-full.png`
  스크린샷을 직접 Read(이미지)로 열어 표가 뷰포트 폭 안에 깔끔하게 들어가고 레이아웃 깨짐이 없음을
  육안으로도 확인했다. `git status --short`로 이번 측정으로 `design/` 폴더의 어떤 파일도 변경되지
  않았음(출력 없음)을 확인했다.
- git add/commit/push는 개발팀이 직접 하지 않았다(검증 성격 작업이라 저장소 변경 자체가 없었음).

**특이사항**

- 범위를 벗어나는 수정은 없었다. 스크래치 디렉터리 밖에는 아무 파일도 남기지 않았다.
