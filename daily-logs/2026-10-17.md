## 개발팀

**오늘 지시한 일**

1. 작업 시작 전 Bash 사용 가능 여부 먼저 확인하도록 지시(과거 반복된 문제 재확인
   차원).
2. `scripts/validate_posts.sh`의 "frontmatter date 필드 검사"(3-2)가 date 필드가
   **있을 때만** 파일명과 일치하는지를 검사하고, date 필드가 **아예 없는 경우**는
   전혀 FAIL 처리하지 않는 공백을 마스터가 코드 직접 대조로 발견해 지적. `design/style-guide.md`
   작성일 표시 규칙과 `generate_sitemap.sh`/`generate_jsonld.sh`의 lastmod/datePublished
   우선 사용 로직이 모두 date 값 존재를 전제하므로, "date 필드가 아예 없으면 FAIL"
   검사를 추가하고 회귀 테스트(`scripts/test_required_date_field.sh`) 신설 + `daily_check.sh`
   14단계 편입을 지시. 수정 범위는 `validate_posts.sh`, 신규 테스트 파일,
   `daily_check.sh` 3개로 한정(`posts/`, `seo/`, `design/`, 다른 generate 스크립트는
   건드리지 않음).

**완료한 일 (마스터 재검증 완료)**

- 개발팀이 `echo test && pwd` 실행에 성공해 Bash를 정상적으로 사용할 수 있었다고
  보고. `REQUIRED_FIELDS`에 `date`를 추가해 기존 필드 검사 로직을 재사용하는 방식으로
  구현했고, 신규 회귀 테스트((a) date 없음→FAIL, (b) date 있음→PASS) 작성, `daily_check.sh`를
  "[1/14]~[14/14]"로 갱신했다고 보고.
- 전체 실행 중 **기존 `test_duplicate_slug.sh`의 fixture 생성 함수(`make_valid_post()`)가
  date 필드를 넣지 않아, 오늘 추가한 필수 검사 때문에 그 테스트의 정상 케이스가
  FAIL로 오판되는 문제를 개발팀이 스스로 발견**했고, 지시된 3개 파일 범위를 벗어나는
  4번째 파일(`test_duplicate_slug.sh`) 수정이 필요하다고 판단해 임의로 고치지 않고
  마스터에게 승인을 요청했다. 마스터가 "파일명 날짜와 일치하는 `date:` 한 줄만
  추가, 기존 슬러그 중복 검출 로직은 건드리지 말 것"으로 범위를 명시해 승인하고
  재검증까지 지시했다. 개발팀이 수정 후 `bash scripts/test_duplicate_slug.sh`(PASS,
  exit 0), `bash scripts/daily_check.sh`(1~14단계 전부 성공, exit 0)를 모두 재실행해
  확인했다고 보고.
- **마스터 직접 재검증**: `git diff --stat`으로 변경 파일이 지시/승인 범위 내
  4개(`validate_posts.sh`, `test_required_date_field.sh`, `daily_check.sh`,
  `test_duplicate_slug.sh`)로 한정됨을 확인. `bash scripts/test_required_date_field.sh`,
  `bash scripts/test_duplicate_slug.sh`, `bash scripts/validate_posts.sh`(실제 `posts/`
  대상), `bash scripts/daily_check.sh`를 마스터가 직접 모두 재실행해 보고된 출력과
  정확히 일치함을 확인했다(전부 `$?`로 exit 0, `daily_check.sh`는 1~14단계 전부
  "성공"). `git diff scripts/validate_posts.sh scripts/test_duplicate_slug.sh`로 코드
  변경 내용도 직접 리뷰해, date 필수 검사와 3-2(날짜 일치 검사)가 역할 분리된 주석과
  함께 깔끔하게 구현됐음을 확인했다. `seo/` 디렉터리는 스크립트 실행으로 재생성됐지만
  내용이 기존과 동일해 `git status`에 변경으로 나타나지 않음을 확인했다(`posts/`,
