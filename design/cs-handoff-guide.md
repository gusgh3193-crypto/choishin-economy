# CS팀 전달 신고 1차 판단 가이드 (디자인팀)

## 0. 이 문서의 목적

CS팀은 `cs/inquiry-log.md` 3번("개발팀·기획팀 전달용 오류·불만 신고 요약 양식")을 통해 접수된
신고 중 "전달 대상"이 디자인팀으로 지정된 건(화면 표시·가독성·색상·레이아웃 관련: 글자 크기,
줄 간격, 색상 대비, 표·카드뉴스 디자인 등)을 전달받는다. 이 문서는 디자인팀이 그런 신고를
받았을 때 **가장 먼저 무엇을 기준으로 1차 판단**하는지를 정리한 것이다.

- 판단 기준 문서: `design/style-guide.md`, `design/color-palette.md`
- 접수 양식 근거: `cs/inquiry-log.md` 3-2번 표의 "전달 대상" 행(2026-09-21 CS팀 개정)
- 이 문서는 새 규칙을 만드는 것이 아니라, 이미 정해진 두 문서(스타일 가이드/색상 팔레트)를
  **신고 건에 어떻게 적용해 1차로 분류할지**에 대한 절차 문서다.

이 문서를 작성하는 시점(2026-09-21)까지 `cs/inquiry-log.md`에 디자인팀으로 전달된 실제 신고는
없다(사이트 자체가 아직 배포되지 않았기 때문). 따라서 아래 내용은 앞으로 실제 신고가 들어왔을 때
쓸 절차이며, 이 문서 안의 신고 사례는 모두 "예시(가상)"이다.

---

## 1. 1차 판단 절차 — 3단계

디자인팀은 전달받은 신고를 다음 순서로 확인한다.

### 1단계: 신고 내용을 기존 기준 문서와 대조한다

신고 내용을 `design/style-guide.md`와 `design/color-palette.md`에 이미 정의된 구체적 수치/규칙과
직접 대조한다. 특히 다음 항목을 우선 확인한다.

- **명도 대비**: style-guide.md 8번 "접근성 고려사항"에 정의된 본문 기준 **4.5:1 이상**
  (큰 텍스트는 3:1 이상), 그리고 color-palette.md 2번 "명도 대비 계산"에 이미 계산돼 있는 팔레트별
  대비비 표.
- **폰트 크기**: style-guide.md 7번(모바일 화면 가독성)·8번(접근성)에 정의된 **본문 16px(1rem)
  이상** 기준.
- **줄 간격**: style-guide.md 2번에 정의된 **1.7~1.8배** 권장치(WCAG 1.4.8의 1.5배 이상 기준을
  상회).
- **표/코드 블록 구조**: style-guide.md 3번(표), 6번(코드 블록), 8번(표 접근성 `<th scope="col">`)
  기준.
- **색상 값 자체**: color-palette.md 1번 "팔레트 요약 표"에 정의된 실제 hex 코드
  (`--color-text: #333333`, `--color-link: #0B5FA5` 등, 4번 CSS 변수 제안 참고).

### 2단계: "확인된 이슈"인지 "단순 의견"인지 분류한다

| 분류 | 정의 | 처리 방향 |
|---|---|---|
| **확인된 이슈** | 신고 내용이 위 1단계 기준 문서의 구체적 수치/규칙을 실제로 위반하는 경우. 즉 이미 정해둔 기준 자체는 맞는데 구현(또는 구현 예정 값)이 그 기준에 못 미치는 경우. | 아래 2번(개발팀 전달 여부 판단) 절차로 넘어간다. 관련 문서(style-guide.md/color-palette.md)나 실제 구현을 수정 검토 대상으로 남긴다. |
| **단순 의견(취향)** | 신고 내용이 기존 기준을 위반하지는 않지만, 신고자 개인의 미적 선호("다른 색이 더 예쁠 것 같다", "글씨체가 마음에 안 든다" 등)에 해당하는 경우. | 기존 가이드에 이미 근거(대비 계산, 톤앤매너 근거 등)가 있으므로, 그 근거를 들어 **규칙을 임의로 바꾸지 않는다**. 필요하면 의견으로만 기록하고 반영 여부는 별도 검토 대상으로만 남긴다(즉시 변경하지 않음). |

판단 근거는 반드시 구체적 수치/문서 위치를 인용한다. 예: "신고된 링크 색 `#0B5FA5`는
color-palette.md 2-2번에서 대비비 6.57:1로 계산돼 4.5:1 기준을 통과하므로 위반이 아니라 단순
의견으로 분류한다"처럼, "느낌"이 아니라 근거 문서의 숫자를 근거로 든다.

**주의**: 신고 내용이 기준 문서에 아예 정의되지 않은 새 영역(예: 카드뉴스 디자인 세부 규칙처럼
아직 style-guide.md/color-palette.md에 수치화되지 않은 부분)을 지적하는 경우는 "위반"도 "단순
의견"도 아닌 **"기준 미비"**로 별도 표시하고, 필요시 기준을 새로 제정할지 여부를 검토한다(이때도
임의로 즉흥 결정하지 않고, 기존 문서의 근거(접근성 원칙, 톤앤매너 원칙)와 일관되게 검토한다).

### 3단계: 처리 방향을 기록한다

디자인팀 내부 검토 결과는 신고 건별로 간단히 기록해 CS팀/마스터가 추적할 수 있게 한다
(형식은 이 문서의 3번 참고).

## 2. 개발팀 전달이 필요한 경우 vs 디자인팀 문서 선에서 끝나는 경우

"확인된 이슈"로 분류되더라도, 처리가 어디서 끝나는지는 다르다.

- **디자인팀 문서 선에서 끝나는 경우** (개발팀 전달 불필요):
  - 신고 내용이 이미 style-guide.md/color-palette.md에 규칙이 있는데, **문서 자체의 설명이
    불충분하거나 문구가 애매해서** 오해를 일으킨 경우. 이때는 가이드 문구를 보완하는 선에서
    끝난다(실제 코드/CSS 변경이 필요한 게 아니므로).
  - 예시(가상): "표가 왜 이렇게 생겼는지 모르겠다"는 의견이 실제로는 style-guide.md 3번 규칙을
    신고자가 오해한 데서 비롯된 경우 → 문서 설명 보완만 검토.
  - 사이트가 아직 배포되지 않아 **아직 실제 CSS/구현물 자체가 존재하지 않는** 단계에서는, "확인된
    이슈"라 해도 지금 당장 개발팀에 전달할 구현물이 없으므로, 우선 style-guide.md/color-palette.md
    쪽 기준을 재확인·보완하는 선에서 남겨두고, 실제 전달은 아래 항목처럼 "배포 이후" 시점에 이뤄진다.

- **개발팀에도 전달이 필요한 경우**:
  - 신고 내용이 **이미 정해진 기준을 실제 구현이 위반**하는 경우, 즉 CSS/HTML 등 실제 코드
    수정이 필요한 사안. 예: 실제 배포된 화면에서 본문 폰트가 16px 미만으로 렌더링되고 있다거나,
    링크 색상의 실제 대비가 계산값과 다르게 나오는 경우.
  - 이 경우 디자인팀은 `cs/inquiry-log.md` 3-2번 양식과 동일하게, "무엇이(기준) - 무엇을(신고
    내용) - 어떻게 다른지(위반 근거)"를 정리해 개발팀에 전달한다. 디자인팀은 원인 분석이나
    구현 방법까지 결정하지 않고, 위반 사실과 기준 근거를 전달하는 데 집중한다
    (`cs/inquiry-log.md` 3-1번의 "CS팀이 임의로 결론 내리지 않는다" 원칙과 동일한 취지).

## 3. 현재 사이트 미배포 상태에서의 처리 한계 (필수 명시)

CLAUDE.md에 명시된 대로, 최신경제는 아직 실제 배포 플랫폼이 정해지지 않아 **사이트가 라이브로
존재하지 않는다**. 따라서 디자인팀이 "화면에서 실제로 어떻게 보이는지"를 신고 내용과 비교해
직접 확인하는 것은 현재 불가능하다.

이는 `design/review-2026-09-13-interest-rate-impact.md`에서 이미 쓰인 표기 관행과 동일하게,
아래 원칙을 그대로 따른다.

- 디자인팀이 신고를 받으면, **마크다운/가이드 문서 차원**(style-guide.md·color-palette.md에
  정의된 수치, 마크다운 구조)에서만 1차 판단이 가능하다.
- 신고 내용이 "실제 렌더링 화면"(브라우저에서의 실제 픽셀 크기, 실제 계산된 대비, 실제 CSS
  적용 여부 등)에 관한 것이라면, 사이트가 배포되기 전까지는 **"확인 못 함"**으로 명시하고,
  실제 확인은 배포 이후로 미룬다. "아마 괜찮을 것"이라고 추정해서 "통과"로 판정하지 않는다.
- 예: 신고 내용이 "글자가 작아 보인다"는 것이라면, style-guide.md 7번·8번의 "본문 16px 이상"
  기준 자체는 이미 정해져 있음을 확인할 수 있지만(문서 차원 확인 가능), 실제 배포된 화면에서
  폰트가 몇 px로 렌더링되는지는 사이트가 없어 **확인 못 함**으로 남긴다.
- 마찬가지로 카드뉴스 시안(SVG/HTML)처럼 디자인팀이 직접 만든 산출물이 있는 경우는 해당
  파일을 열어 규칙 위반 여부를 확인할 수 있으므로 이 경우는 "확인 못 함"의 예외로 취급한다
  (파일이 실제로 존재하면 Read로 열어 직접 확인).

## 4. 신고 건 기록 형식 (디자인팀 내부용)

`cs/inquiry-log.md` 3-2번 양식으로 전달받은 신고를 디자인팀이 처리할 때, 아래 항목으로 1차
판단 결과를 남긴다(형식은 CS팀 양식과 짝을 이루도록 구성).

| 항목 | 작성 방법 |
|---|---|
| 접수일 / CS 전달일 | `cs/inquiry-log.md` 3-2번 표의 접수일과, 디자인팀이 전달받은 날짜 |
| 신고 내용 요약 | CS팀이 전달한 "구체적 문제 내용" 그대로 요약 |
| 대조한 기준 문서 | `design/style-guide.md` 몇 번 항목 / `design/color-palette.md` 몇 번 항목인지 명시 |
| 1차 판단 | 확인된 이슈 / 단순 의견(취향) / 기준 미비 중 하나, 근거 수치 포함 |
| 렌더링 확인 여부 | 사이트 미배포 상태면 "확인 못 함(배포 후 재확인 필요)"으로 명시. 배포 후라면 실제 확인 결과 기재 |
| 후속 조치 | 디자인팀 문서 선에서 종료 / 개발팀 전달 필요(전달 사유 포함) 중 하나 |

## 5. 요약

1. 신고를 받으면 먼저 style-guide.md·color-palette.md의 구체적 수치(대비 4.5:1, 폰트 16px,
   줄 간격 1.7~1.8배 등)와 대조한다.
2. 기준 위반이면 "확인된 이슈", 위반이 아닌 개인 취향이면 "단순 의견"으로 분류하고, 단순 의견은
   기존 가이드 근거를 들어 규칙을 임의로 바꾸지 않는다.
3. 기준 자체가 없는 새 영역이면 "기준 미비"로 별도 표시한다.
4. 실제 CSS 구현이 필요한 위반은 개발팀에도 전달하고, 가이드 문구 보완만으로 끝나는 사안은
   디자인팀 문서 선에서 처리한다.
5. 사이트가 배포되기 전까지 "실제 화면에서 어떻게 보이는지"는 항상 **확인 못 함**으로 남기고,
   배포 후 재확인을 전제로 한다.
